# CRM Inbox usability and synchronization follow-up

The conversation history shown by the CRM is its local store, not a direct live Telegram history view. Initial import fetches a bounded recent page and older pages are fetched on request. Interruptions can leave a gap; no comparison with the user's real Telegram history was performed in this change.

The explicit **Refresh recent messages** action imports up to 100 latest messages through the conversation's fixed account, preserving the separate older-history cursor and exhausted state. It does not prove that a larger gap is completely filled, detect deletions, or replace reconciliation. Older messages remain available via **Load older messages**. Refresh failure is displayed and can be retried.

The thread displays calendar-day separators and sorts messages sharing a timestamp by Telegram message ID. Outgoing read receipts are shown only when the stored Telegram read state or the account's outbox watermark confirms them; read events refresh only the affected active thread. Unknown provider outcomes remain unknown. The composer uses a compact field and an expanded editor sharing the same draft and approval state. Sales history is requested only when an authorized user opens the details panel; an unlinked contact cannot have a reliable sales summary.

AI Leads uses a single-column compact layout and the discovery page opens on candidates; workflow filters and source options are collapsed. Inbox filters and labels use synced Telegram folder tags for linked clients and the matching account. Unlinked dialogs have no stored folder memberships, so this is not yet a complete Telegram-folder mirror. Existing source permissions and deployment policy remain in force. Telegram folders for channel discovery, full folder membership for unlinked dialogs, iterative AI coaching and verification against real account history and real advertising sources remain outstanding.

Runtime cost: one bounded MTProto page and a transaction per explicit recent refresh, no new background timer or idle polling. Read-state events can refetch the active conversation detail and its loaded message pages; inactive queries are only marked stale. Sales adds one purchase-history request per opened authorized client panel, not one request per Inbox row. Inbox adds one cached workspace folder-list read and a workspace-scoped tag lookup only when filtering by a folder; the page query joins the linked-client folder tags. Near-bottom scrolling fetches one bounded cursor page at a time. No 100-channel or production load measurement was performed.

Manual QA: compare a consenting test conversation with Telegram across several dates, including an offline gap exceeding 100 messages, read/unread transitions and older-page loading. Verify account/workspace isolation, unlinked and linked purchase history, small viewport keyboard, expanded editor and saved drafts. Test source-folder selection and real discovery quality only after those features and their approved configuration are available.

## Local runtime conflict and AI configuration

The local Finance compatibility API uses the same application composition as the main API. Both previously attempted to acquire the CRM runtime lease. The Finance launchers now pass `CRM_RUNTIME_ENABLED=false`; the main API keeps the runtime enabled by default. After a startup lease denial, a subsequent explicit CRM request can safely retry acquiring the lease and restore the shared live handles; there is no new polling. A running launcher must be restarted for its new child environment to take effect. The lease remains necessary and a competing remote owner can still correctly cause 409. This change was not validated against the user's live Telegram session; do not force-release the lease or launch a second session.

2026-11-01 recheck: the lease owner ID stayed the same and its expiry advanced while both local API children restarted. The owner is an external instance using the same database. Local CRM commands still return 409 until requests are routed to that owner or the external runtime is intentionally disabled and its lease expires. The available Railway API token did not authenticate for read-only deployment inspection; no deployment setting was changed. The frontend now reconciles on its first successful CRM event stream connection and keeps reconnecting while visible, so an ordinary page open can receive subsequent changes without manual Refresh.

The `.env` file, not `.env.example`, supplies the API configuration. `INTERNAL_AI_ENABLED=true` and a valid backend `INTERNAL_AI_OPENAI_API_KEY` enable only the gateway. The Business workspace now has one explicit `scope: WORKSPACE` processing grant, so Copilot uses the approved reference for every current and future Business CRM contact without per-chat setup. Other workspaces remain blocked. AI execute permission, an enabled workspace/category and finite daily/monthly/per-request budgets still apply; the Business workspace and manual Sales categories were configured. Discovery separately requires `INTERNAL_LEAD_DISCOVERY_ENABLED=true`, an accessible account and correctly scoped `INTERNAL_LEAD_DISCOVERY_GRANTS`; the four public Business sources are visible but paused until account access and immutable channel IDs are verified. Restart the API after changing environment settings.

The four public sources and Business AI budget/category records were created in the connected database. No paid provider request or Telegram collection was made during setup.
