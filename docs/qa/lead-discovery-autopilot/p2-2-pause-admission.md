# Pause and AI admission contract

Scope: automatic Lead Discovery queue execution. Pause and admission serialize on the PostgreSQL source row across API instances. Admission commits a RUNNING AiOperation and reserves budget in the same transaction as the source/claim/permission guard. If pause commits first, a later admission is rejected. If admission commits first, the operation is already permitted: the provider call may start or finish after pause returns. Pause is not a guarantee of no subsequent network sends, cancellation, or zero additional charges. Manual analysis and other AI categories have their existing separate contracts.

The API exposes `admittedAiOperations`: source-related automatic LEAD classification/extraction operations currently recorded as RUNNING, including those admitted before pause but not yet dispatched. A stranded RUNNING receipt may represent an unknown outcome and still requires reconciliation. The count is derived from saved observations and operation receipts, and is not a count of live provider connections. UI refresh is explicit; it is a snapshot, not a streaming guarantee.

No transaction is held during provider execution. Settlement remains idempotent and writes the durable response with the receipt. Business writes retain claim/source fencing. If admission is denied by pause, an unadmitted operation identifier can be reset only while the same claim is still valid, under the source lock and after confirming the operation does not exist. UNKNOWN paid outcomes are never automatically repeated. A saved result is replayed after resume without another provider call, subject to current authorization and fencing.

The guard uses the current instance's configured processing grants, checked under the source lock. Pause is database-coordinated, but environment-based grant configuration is not a distributed live revocation mechanism: every instance must receive the updated configuration, and an operation admitted before revocation may still be sent. Workspace authorization changes and external provider-side cancellation do not participate in this source-row lock. Do not claim stricter semantics without a coordinated dispatch protocol and coordinated grant revocation.

Run `lead-durable-ai.integration.spec.ts` with `LEAD_EXECUTOR_TEST_DATABASE_URL` set to a dedicated fully migrated PostgreSQL database. The tests use two Prisma clients and a mock provider; they cover both lock orderings, pause before and after admission, provider in flight, settlement before candidate, resume and restart, revoked grant, UNKNOWN and provider call counts. Run `lead-pipeline.integration.spec.ts` in a separate dedicated database. Integration tests use `--forceExit` because existing test infrastructure leaves handles open. No real provider or Telegram is used.

Cost: no new polling, timers, persisted rows or external calls. Each new admitted automatic AI operation takes one source row lock and reads the auto configuration inside its existing admission transaction. A selected-source progress request adds one bounded-by-source SQL aggregate over observations/AI operations; it is not polled globally. Idle database and Railway baseline are unchanged. At 100 sources, cost scales with actual AI admissions and explicit progress reads; hosted concurrency, connection contention and retention have not been load-tested here.
