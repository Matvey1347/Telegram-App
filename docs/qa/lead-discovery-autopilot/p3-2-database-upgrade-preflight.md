A read-only Prisma schema diff against the live datasource failed with P1001, so the current working schema was not proven identical to the reconstructed schema and production drift is unresolved. A production-sized or data-bearing restore rehearsal was not performed. Do not represent the local result as verification of the actual database upgrade.

## Approval and operational plan

1. Confirm the actual Railway service, deployment SHA, database/branch identity, runtime owner, flags, current migration checksums, and backup/restore access using the provider's authorized read-only controls. Assess table sizes, DDL lock duration and maintenance window. Freeze and review the exact migration artifacts and application revision.
2. Take an approved encrypted backup and verify restore to a separate protected database with no live Telegram runtime; exclude credentials/session material from logs and artifacts. If actual data is restored, maintain its access/retention controls. On this isolated restored copy run `db:deploy:safe`, schema verification and status, re-run it for idempotence, check representative CRM and AI data and the concurrent promotion regression. Never connect copied MTProto sessions.
3. Investigate historical checksum differences and actual pre-upgrade schema drift; resolve via a reviewed, forward-compatible procedure without rewriting applied migrations. Resolve or explicitly risk-accept the flaky test. Verify rollback compatibility with the old application on the migrated restored database, including triggers and existing UNKNOWN/financial state.
4. Only after separate authorization, take/verify a fresh backup, disable new automation without discarding in-flight work, keep `INTERNAL_AI_ENABLED=false`, and deploy the reviewed release through Railway's safe pre-deploy with a controlled single runtime owner. A migration and a runtime restart are separate authorized actions. Confirm lease handoff and one connected owner after rollout; do not force the lease or reuse the same session in another environment.
5. Verify migration status, schema, application health, existing CRM/AI data and queue states. Enable only the scoped source and grant after a further explicit decision. Do not send Telegram messages or markRead in this process.
6. Rollback: stop new Lead Discovery work and preserve `RUNNING`/`UNKNOWN` operations, AI budgets, receipts and durable results. Roll back the app only after compatibility has been established; leave additive schema in place. Database restore is a last-resort, separately authorized operation with a point-in-time and reconciliation plan, since restoring overwrites newer data and may affect sessions and financial state. Do not drop tables or reverse triggers blindly.
