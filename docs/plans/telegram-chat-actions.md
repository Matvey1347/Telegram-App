# Telegram chat actions — Prompt №10

Local implementation, 2026-11-01 Europe/Warsaw. No migration, live Telegram message/file/voice send, paid AI call, Support runtime or release was performed. [QA and acceptance](../qa/telegram-chat-actions/README.md).

## Scope and audit

CRM continues to support private user dialogs owned by an existing MTProto account. This stage does not expand CRM to groups/channels/secret chats. It reuses the account runtime, session lease, recovery, canonical `TelegramCrmMessage`, batch writer, EventHub/SSE, cursor history, existing rich editor and workspace-local drafts. Shared Chat UI receives neutral messages, capabilities and callbacks; CRM permissions, DNC, Telegram IDs and AI rules stay in its adapter.

Grace mapped the actual runtime and reuse points; Parnas/Knuth reviewed file boundaries and source-level costs. Backend transport, domain API and frontend were assigned separate files under one contract. Turing's independent read-only review identified ordering, deletion, notification and retry edge cases; fixes and regressions are recorded in QA. Previous uncommitted stages and unrelated baseline errors are preserved.

## Operation identity, state and reconciliation

New action/media IDs are UTC `YYYY-MM-DD:UUID`. A durable actor/payload-bound receipt is claimed UNKNOWN before a provider mutation, with unique workspace operation identity and partial unique pending target. Changed body/actor/target conflicts. POST replay returns the existing receipt without executing Telegram again. Edit/delete/reaction share a target lock; forward uses its source target, media uses a compact body/destination-context digest, so changing a browser key after reload does not bypass a pending identical operation. Completed operations can be deliberately repeated as a new user action.

GET status is a bounded read, never a retry mutation. Edit compares normalized plain text/entities; reactions compare the actual selected reaction; delete-for-me can reconcile absence. Unknown delete-for-everyone, forward and media cannot always be proven from history and remain UNKNOWN. No blind re-forward/upload occurs after timeout, reconnect or DB failure following Telegram success. These states require explicit operator review; there is no UI action that forges confirmation. This is a safety limit, not a universal exactly-once claim or a claim of distributed event ordering.

Manual text retains the existing Telegram random ID and local unique receipt, plus a durable pre-send claim. It stores a request hash rather than a duplicate original body. The canonical draft retains its key. A lost HTTP response can resolve through receipt GET; null is inconclusive. If Telegram succeeded before local persistence and no exact receipt can be established, ordinary text remains UNKNOWN rather than sending again. Copilot still checks current approval/revision/context/text and DNC immediately before transport; no automatic send or AI attachment analysis is added.

Incoming edit and reaction events are coalesced per message within existing bounded account batches and re-read from Telegram. This avoids trusting unversioned reactions or reversed edits with the same second-level edit date. Full snapshots replace prior presentation metadata while retaining only manual receipt/AI identity. No-op snapshots cause no message write. Edit-before-new emits an update, with no incoming notification or unread increment. Deleted identities prevent delayed new/edit/history resurrection, including deletion before HTTP send persistence.

Deletion IDs without a peer are matched only by exact workspace/account and stored numeric IDs. Body-free tombstones also retain unknown IDs. Known conversations get targeted `GetPeerDialogs` read state; server `pts` rejects stale snapshots with the same read boundary, and a compact watermark prevents queued new messages already represented in that snapshot from incrementing unread again, and a bounded local tail preserves later committed unread messages. Unknown-local deleted IDs cannot safely identify a peer; they are tombstoned without guessing. Existing explicit bounded sync is needed if an account's unloaded dialog counters require reconciliation.

Deleting a message clears its body/media presentation, recomputes latest visible preview and retires the existing notification group conservatively. Delivery-time authorization additionally batch-checks the referenced message is still present and not deleted; another remaining unread message cannot authorize a queued deleted-message preview. Already delivered external push cannot be retracted. CRM sales/payment/activity history is unchanged.

## Media, voice and security

Private chat media does not reuse public immutable managed-post storage. Upload is one bounded multipart file; server rejects excess multipart fields/parts and unsafe names, validates allowed MIME/signatures and voice container, and never fetches a user-supplied URL. Native Telegram media identifiers stay server-side and are refreshed through the exact authorized account/message. No bytes/base64 are written into PostgreSQL or operation receipts.

Two transfers/process are admitted before multipart buffering, with another two-transfer bound at the shared transport and one SDK upload worker. There is no waiting queue. Downloads use bounded chunks with cleanup; HTTP returns private/no-store, nosniff, safe attachment disposition and bounded length. Buffers are request-scoped; no temp history, B2/Redis service, permanent media cache or new deployment is introduced. Disconnection/cancel may stop the browser wait without undoing an already dispatched remote operation; UI keeps UNKNOWN appropriately. Media larger10MiB and unsupported formats fail explicitly.

Voice requires actual Ogg pages/Opus identification, coherent stream/page boundaries and duration≤600s. A local small Ogg/Opus fixture validates mock tests; runtime adds no FFmpeg or transcoding worker. Browser permission denial, pending permission cancellation, late stream cleanup, recording preview and explicit audio-file fallback are covered. A browser audio blob is never silently presented as Telegram voice. Recordings are not transcribed or sent to AI.

Images/audio load only after explicit interaction; object URLs/streams are released by the UI. Byte caps do not constitute measured decoded-image pixel/RSS limits. Test actual device behavior and unusually large image dimensions on staging before increasing limits. Downloaded documents are attachments, not executable inline HTML. Text renders through safe entity-aware React presentation; links use approved schemes, and JS UTF-16 slicing preserves Unicode offsets.

## Schema, retention, rollout and rollback

Additive migration `20261101130000_telegram_chat_actions`: `TelegramCrmMessage.deletedAt`; conversation unread snapshot watermark; compact operation receipts with workspace operation uniqueness and pending-target partial index; account/workspace cascade and account/retention indexes; body-free account/message deletion identities with account cascade; workspace/account/numeric-message index. Existing canonical messages remain the single message store.

Confirmed/failed non-TEXT receipts older30 days are deleted in a bounded20k batch during existing daily maintenance. UNKNOWN receipts remain until verified/operator/account lifecycle cleanup, since dropping a pending claim would permit duplicate forwarding/upload. TEXT receipts and body-free deletion identities survive with their account and cascade when the workspace/account is removed. Pending edit requests retain at most4096 code units for reconciliation; ordinary text receipts contain hashes only. No new cleanup wake/cron is created. Monitor aggregate pending growth/retention capacity before broad rollout; don't erase unknown evidence to force a retry.

Default deployment flags: `CRM_CHAT_ACTIONS_ENABLED=false`, `CRM_CHAT_MEDIA_ENABLED=false`. Ordinary manual text remains usable. Stage rollout: apply migration, deploy shared/API/web together, fix the five existing global API build errors, enable actions for a controlled environment/account with existing CRM Send settings, then media. Verify real staging Telegram capabilities with consenting test peers, current permissions, provider rejections, connection loss and actual iOS/PWA before expansion. No production migration or final release is authorized by this local implementation.

Rollback first disables the flags; status reconciliation/read history remain available and legacy text works. Retain additive columns, tombstones and unknown receipts. Do not roll back to code that resurrects messages, retries unknown sends, or exposes private media publicly. A destructive schema reversal requires separately reviewed data export and account/message receipt retention; no automatic destructive down migration is supplied.

## Cost model

Idle feature work is zero new query/write, provider request, timer, stream, account connection, worker or deployment. Existing account runtime/SSE/recovery remains.100 stored accounts/channels do not create one connection per conversation; existing runtime startup/account bounds still apply. There is one extra bounded receipt cleanup query during the existing daily wake.

Source-level action costs include compact receipt, current target/context checks and authoritative store; exclude membership/role graphs, transaction protocol, session setup and Prisma relation expansion. Ordinary edit/reaction is approximately10–14 logical data calls and up to4 Telegram calls (domain current read, transport validation, mutation, confirmation). A duplicate confirmed receipt needs only scope/receipt/projection reads and zero provider mutation. Unchanged full snapshots avoid message writes; receipt bookkeeping still changes once per deliberate operation. Delete adds bounded tombstone/row/group updates plus a targeted dialog read; live deletion costs scale with affected known conversations, never all clients. Event edits/reactions add one coalesced current-message read per affected ID and one account-scoped batch lookup. No exact invoice/query-count saving is claimed.

| Volume/day | Edit/react logical calls at10–14/action | Telegram requests up to4/action | Payload at10MiB uploaded/action |
| --- | ---: | ---: | ---: |
|100 |1,000–1,400 |400 |0.98GiB |
|1,000 |10,000–14,000 |4,000 |9.77GiB |
|10,000 |100,000–140,000 |40,000 |97.66GiB |

Those are separate workload scenarios, not the assumption that every text action uploads10MiB. A small100KiB attachment is100×less payload than10MiB. Upload receives browser bytes and sends them to Telegram; each lazy download receives Telegram bytes and sends them to the browser, plus protocol overhead. Two10MiB chunked downloads can transiently hold about40MiB payload during concatenation, before SDK/HTTP/Node overhead; no measured Railway RSS/CPU/latency claim is made. Ogg validation scans at most10MiB; decoded image/audio memory remains a device/staging measurement. At10k actions/day, retention/index/Neon wake and Railway egress need measured capacity review before lifting caps.

Known limits: current private-peer CRM scope; curated standard reaction UI rather than premium catalog discovery; no paid reactions; no guaranteed voice on browsers lacking native Ogg/Opus; no physical-iPhone proof; no reliable cancellation after provider dispatch; unknown outbound outcomes may require operator investigation; no universal cross-instance realtime ordering guarantee; baseline repository failures prevent a clean release gate. Test-only Support adapter demonstrates presentation reuse with different capabilities, not a production Bot Support product.
