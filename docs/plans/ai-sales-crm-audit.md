# AI Sales CRM: технический аудит и план реализации

Дата аудита: 30 октября 2026 года. Область: код текущего монорепозитория; production-трейсы, тарифы, активность пользователей и планы запросов не предоставлены. Этот документ не является разрешением на автоматическую отправку сообщений или сбор данных из произвольных источников.

## 1. Краткий вывод

Существующая CRM уже имеет MTProto adapter, ограниченную очередь обновлений, пакетную запись, workspace-scoped модели, cursor pagination истории, ручную отправку с idempotency key, SSE endpoint, Operations Notifications, Web Push и scheduled task для ежедневной синхронизации. Их следует развивать, а не создавать параллельную CRM. При этом веб-хук `useTelegramCrmRealtime` не вызывается production-кодом, поэтому live-события сейчас не доходят до TanStack Query. Входящие Operations Notifications и Web Push выключены явным `return false`. Глобальный MTProto lease делает запись в PostgreSQL каждые 30 секунд при активном runtime. Это подтверждённые факты кода, а не измеренное объяснение всей задержки UI.

## 2. AS-IS: фактический путь данных

1. `TelegramCrmMtprotoAdapter` нормализует MTProto updates; manager открывает выбранные аккаунты, подписывается на `handle.onUpdate`, ограничивает очередь и запускает recovery: [runtime-manager.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-runtime-manager.service.ts#L70), [runtime-manager.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-runtime-manager.service.ts#L245), [runtime.policy.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-runtime.policy.ts#L8), [adapter.ts](../../apps/api/src/telegram/shared/mtproto/telegram-crm-mtproto.adapter.ts).
2. Batch store разрешает conversation по workspace/account/user и передаёт сообщения в message writer. Writer дедуплицирует Telegram ID, делает `createManyAndReturn(skipDuplicates)`, обновляет compact поля conversation и после commit публикует события: [batch-store.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-batch-store.service.ts#L49), [message-batch-writer.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-message-batch-writer.service.ts#L61), [message-after-commit-publisher.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-message-after-commit-publisher.service.ts#L27).
3. Схема хранит peer, conversation, message и account sync state с составными workspace FK и индексом истории `(conversationId,sentAt,id)`: [schema.prisma](../../apps/api/prisma/schema.prisma#L2635), [schema.prisma](../../apps/api/prisma/schema.prisma#L2699).
4. После commit `TelegramCrmEventHub` публикует события в локальный RxJS `Subject`, а SSE controller фильтрует их по workspace и собственному/общему доступу: [event-hub.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-event-hub.service.ts#L5), [events.controller.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-events.controller.ts#L18). Это события только внутри процесса API; при нескольких инстансах доставка браузеру через другой инстанс не гарантируется.
5. Frontend API умеет читать SSE, а хук умеет закрывать поток в скрытой вкладке и выполнять reconciliation после reconnect: [telegram-crm-api.ts](../../apps/web/src/lib/features/growth/telegram-crm-api.ts#L359), [use-telegram-crm-realtime.ts](../../apps/web/src/lib/features/growth/use-telegram-crm-realtime.ts#L32). `rg useTelegramCrmRealtime apps/web/src --glob '!*.test*'` показывает только определение; production UI его не монтирует. Поэтому шаг SSE → Query → UI пока отсутствует.
6. Для входящих сообщений projector сразу возвращает пустой результат, так что текущая цепь до Operations Notifications/Web Push не активна: [incoming-notification-projector.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-incoming-notification-projector.service.ts#L24), [incoming-notification-projector.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-incoming-notification-projector.service.ts#L326). Общий push уже поддерживает предпочтения, ограничение устройств и bounded fanout: [operations-web-push.service.ts](../../apps/api/src/domains/operations/notifications/operations-web-push.service.ts#L26). Service worker показывает push и обрабатывает переход, но не содержит fetch/cache/offline обработчиков: [sw.js](../../apps/web/public/sw.js#L11). Offline inbox и очередь отправки сейчас не реализованы; для PWA первым этапом нужен online inbox + push, offline send по умолчанию не вводить.

### Read/unread и контакты

Live incoming создаётся как `UNREAD`, snapshot/history как `UNKNOWN`; сервер поддерживает conversation compact `unreadCount`, а Telegram read updates обновляют watermark и message rows: [message-batch-writer.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-message-batch-writer.service.ts#L95), [batch-store.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-batch-store.service.ts#L201). Нужна явно сформулированная семантика `UNKNOWN` при импортированной истории, потому что локальный unread не равен гарантированному состоянию Telegram до reconciliation. Контакты — `TelegramAdvertiser`, peer может быть привязан через `contactId`; inbox сейчас показывает только непривязанные peer [schema.prisma](../../apps/api/prisma/schema.prisma#L2635), [inbox-read.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-inbox-read.service.ts#L61). Поэтому «единый список диалогов» требует нового read model, но не второй сущности CRM.

## 3. Подтверждённые проблемы и области для измерения

**Подтверждено кодом:**

- Realtime хук не подключён к UI; после внешнего входящего сообщения открытые Query-кэши не получают SSE reconciliation. Существующий hook ограничивает reconnect шестью попытками и переходит в paused [use-telegram-crm-realtime.ts](../../apps/web/src/lib/features/growth/use-telegram-crm-realtime.ts#L8).
- Общий Query provider задаёт stale 4 минуты, GC 45 минут, выключает focus refetch и включает reconnect refetch; CRM отсутствует среди persisted query keys [query-provider.tsx](../../apps/web/src/providers/query-provider.tsx#L16), [query-provider.tsx](../../apps/web/src/providers/query-provider.tsx#L135). Это важно для «мгновенного» повторного открытия и PWA, но изменение persistence требует workspace/account isolation и лимита размера истории.
- Входящие уведомления намеренно выключены без пояснения причины в комментарии; причина исторического продуктового решения неизвестна. Projector уже содержит grouping по contact/conversation, recipient selection и idempotent upsert, которые надо проверить перед включением [incoming-notification-projector.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-incoming-notification-projector.service.ts#L88).
- Runtime lease: один глобальный lease на 90 секунд, продление каждые 30 секунд через `ScheduledTaskLease.updateMany`; это около 2 880 update/day при непрерывно живом runtime, независимо от сообщений [runtime-lease.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-runtime-lease.service.ts#L9), [scheduled-task-lock.service.ts](../../apps/api/src/domains/operations/scheduled-tasks/scheduled-task-lock.service.ts#L54). Lease защищает StringSession от одновременных подключений и не должен удаляться без равноценной эксклюзивности.
- Inbox SQL использует `OFFSET`, `GROUP BY` и сортировку по `MAX(lastMessageAt)`, затем дополнительно count и aggregate [inbox-read.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-inbox-read.service.ts#L70). Это потенциальный рост latency на больших workspace, а не доказанная причина текущей медленной загрузки.
- Query-код местами инвалидирует семейства `contactLists`/`conversationLists`, что на активных экранах может давать широкие refetch: [crm-inbox.tsx](../../apps/web/src/components/features/growth/ad-sales/crm/crm-inbox.tsx#L60), [crm-conversations.tsx](../../apps/web/src/components/features/growth/ad-sales/crm/crm-conversations.tsx#L138). Нужна запись реального query fanout прежде чем оценивать объём лишнего трафика.
- Список inbox запрашивает пять summaries на peer и вложенный last message [inbox-read.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-inbox-read.service.ts#L24). Отдельного HTTP N+1 здесь нет; стоимость вложенного Prisma relation load должна быть измерена в SQL trace.
- Contact list делает rows/count, затем несколько summary/facet запросов; его read model включает связанные tags, peers, contacts, sale/placements и cross-promotion data: [contact-read.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-contact-read.service.ts#L115), [contact-read-model.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-contact-read-model.ts#L41). Sales summary читает совпавшие продажи с вложениями без `take`; размер результата потенциально растёт с историей продаж: [contact-sales-summary.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-contact-sales-summary.ts#L74). Reply summary, напротив, уже батчируется, и не следует ошибочно считать его N+1: [reply-summary.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-reply-summary.ts#L30).
- Локальный `Subject` не даёт cross-instance SSE fanout [event-hub.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-event-hub.service.ts#L5). При нескольких API репликах это correctness-риск, пока не проверена топология Railway.
- При отсутствии live handle `withAccountHandle` открывает временный изолированный MTProto handle [runtime-manager.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-runtime-manager.service.ts#L101). Во время reconnect это потенциальное пересечение для того же StringSession; до расширения send/sync проверить single-session invariant и сериализацию операций.

**Открытые гипотезы:** тяжёлые планы JOIN, медленная авторизация/workspace preflight, отсутствие полезного partial index для inbox, долгие MTProto reconnect, рост CRM message table, N+1 внутри Prisma relation loading и frontend hydration. Подтверждать через endpoint waterfall, Prisma query logs в ограниченном QA, `EXPLAIN (ANALYZE, BUFFERS)` на обезличенной копии и Railway/Neon метрики. Нельзя включать постоянное production query logging ради аудита.

## 4. TO-BE: контракт и архитектура

Единый Inbox read model на базе существующих peer/conversation/contact: компактная строка `{conversationId, peer, contactSummary?, account, lastMessagePreview, unreadCount, attentionStatus, lastActivityAt}`. `GET /telegram-crm/inbox-v2?cursor&limit&status` возвращает `{items,nextCursor,hasMore}`; cursor сортирует `(lastActivityAt,id)` без OFFSET. `GET /conversations/:id/messages?cursor&limit` сохраняет нынешнюю keyset схему. Отдельный `GET /conversations/:id/context` может собрать доступные contact, пакет продаж, цены и права одним purpose-built ответом. Весь API проверяет workspace и `viewOwn/viewAny`, а исходящие мутации требуют явного permission и human action.

Статусы `NEEDS_REPLY`, `WAITING_FOR_CLIENT`, `FOLLOW_UP_DUE`, `INTERESTED`, `CLOSED`, `DO_NOT_CONTACT`, `HUMAN_REVIEW` — отдельное поле внимания conversation/contact с понятными переходами и `statusChangedAt`; `FOLLOW_UP_DUE` выводится из due task или материализуется при наступлении due, а не проверяется ежеминутным full scan. `DO_NOT_CONTACT` блокирует отправку и AI outreach. История статусов нужна как bounded audit событий перехода, не как бесконечный snapshot.

SSE подключить один раз на видимую CRM поверхность, использовать `telegramCrmKeys` и narrow cache patches; на reconnect выполнить один узкий reconciliation по активному inbox/cursor и открытой conversation. События должны иметь `eventId`/monotonic sequence или version для обнаружения пропуска; при нескольких API инстансах нужен общий fanout либо sticky routing с доказанной корректностью. Push идёт через существующие Operations Notifications и service worker, только после workspace flag + пользовательского opt-in, с grouping, quiet hours/приоритетом, suppression при открытом активном чате, dedupe по conversation и отменой при read. Browser visibility не доказывает, что конкретный чат просмотрен; подавление должно быть ограничено подтверждённым presence, а его стоимость и TTL измерены.

AI Copilot — только server-triggered по явному «Создать черновик» или ограниченному business event, не по page view. Контекст: разрешённые сообщения конкретного workspace/conversation, существующие sale/placements, `TelegramAdProduct`, актуальные price snapshots и currency. Результат — предложение ответа, next action, использованные факты/цены и предупреждения; оператор редактирует и подтверждает через существующий manual send. Перед вызовом: DNC/permission/source gates, redaction, лимит контекста, budget/cost cap и idempotency key. После: usage tokens, model/version, request category и стоимость по тарифной таблице, без хранения prompt/полного transcript по умолчанию. Проверять freshness цены непосредственно перед approval/send. Пакет — состав существующей `TelegramAdSale` + placements, а не один канал [schema.prisma](../../apps/api/prisma/schema.prisma#L2262).

Lead Discovery — отдельный bounded use case в `apps/api/src/domains/telegram/telegram-crm/lead-discovery/`, поскольку его результатом является CRM lead и контакт; sales pricing остаётся в `telegram-ad-sales`, MTProto доступ — в `telegram/shared`. Только одобренные источники; собственные каналы и источники имеют разные роли и ACL. Существующий `growth/advertising-sources` описывает источники покупки рекламы для кампаний, поэтому связывание с ним допустимо только после проверки идентичности назначения [advertising-sources.service.ts](../../apps/api/src/domains/growth/advertising-sources/advertising-sources.service.ts#L41). У source фиксировать разрешение, способ доступа, coverage window, cursor, failure/gap state. Сохранить происхождение каждого материала, классификацию `AD`/`MUTUAL`/`UNKNOWN`, confidence и evidence, найденный публичный деловой контакт, нормализованный ключ дедупликации, review status и `expiresAt`. Не превращать найденный контакт в разрешение на массовую рассылку. После human review создавать или связывать существующий `TelegramAdvertiser`, готовить AI draft и экспортировать CSV/XLSX с workspace-scope. `NO_ADS_30D` допустим только если наблюдения покрывают все 30 дней без дыр, источник доступен и известны ограничения Telegram history; иначе `INSUFFICIENT_COVERAGE`.

Instagram — отдельный adapter и webhook ingress, общая модель conversation/read models лишь на уровне канального контракта. Официальный Instagram Login messaging требует Professional Account, токен с `instagram_business_manage_messages`; первым пишет Instagram user, group messaging не поддерживается. Вариант Facebook Login связан с Page и другим набором permissions, Advanced Access/business verification зависят от сценария. Конкретный login flow и доступы выбрать после Meta App Review. Проверка webhook подписи, idempotent event ID, per-workspace account mapping, bounded retry и отправка только в разрешённое окно/контекст обязательны. Не использовать Instagram как канал первого холодного обращения. Источники: [официальная коллекция Meta Instagram API](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api), [официальная коллекция Meta Conversations API](https://www.postman.com/meta/messenger-platform-api/folder/22794852-255610cd-47f5-4f4d-b3fa-71aec360be9a). Конкретные временные окна отправки и entitlement проверять в выбранной версии Meta API перед реализацией; этот аудит не утверждает число часов без подтверждения.

## 5. Схема и индексы: проект миграций

1. Добавить к `TelegramCrmConversation` nullable `attentionStatus`, `attentionChangedAt`, `lastActivityAt` (backfill из `lastMessageAt/updatedAt`), `version` для событий; не менять существующий `state` (ACTIVE/IGNORED/ARCHIVED). Поэтапно backfill батчами и переключить чтение по flag после проверки расхождений.
2. Создать `TelegramCrmAttentionTransition` с workspace/conversation/actor/reason/timestamps, retention или архивированием по согласованной политике. Для prompt metadata — `TelegramCrmAiDraft` с `expiresAt`, approval state, package sale ID и policy version; `TelegramCrmAiUsage` хранит provider/model, token usage, calculated cost/currency, request key и error class без сырого prompt.
3. Lead Discovery: `TelegramLeadSource`, `TelegramLeadObservation`, `TelegramLeadCandidate` и, если требуется аудит отдельного материала, `TelegramLeadEvidence` с уникальными `(workspaceId,sourceId,externalMessageId)` и `(workspaceId,normalizedContactKey)` только там, где семантика ключа однозначна. Существующий advertiser не дублировать. Доступ к Telegram-источнику проверять через имеющийся [TelegramSourceAccessService](../../apps/api/src/telegram/shared/imports/telegram-source-access.service.ts), если его контракт подходит конкретному виду импорта.
4. Индекс кандидата inbox: `(workspaceId, attentionStatus, lastActivityAt DESC, id DESC)` и partial index по active conversations. Для unlinked peers нужен отдельный plan/денормализация latest activity только после `EXPLAIN`; не добавлять индекс ради каждого фильтра. Уже есть message cursor/idempotency и workspace compound FK [schema.prisma](../../apps/api/prisma/schema.prisma#L2690), [schema.prisma](../../apps/api/prisma/schema.prisma#L2722). Индекс `sourceId, observedAt` и `expiresAt` для bounded cleanup. Предложенные индексы проверить на write amplification и нулевой активности.
5. Каждая schema правка сопровождается `apps/api/prisma/migrations/<timestamp>_ai_sales_crm_*/migration.sql`, backfill планом, rollback/feature-flag планом и обновлением shared contracts. Не удалять исторические CRM данные. `CREATE INDEX CONCURRENTLY` и transaction semantics проверять отдельно для выбранного Prisma deployment процесса.

## 7. Cost model и фоновые процессы

Обозначения: `A` активных MTProto аккаунтов, `S` разрешённых источников, `E` входящих событий, `M` обработанных материалов, `D` AI drafts, `U` одновременно открытых видимых CRM клиентов. Числа — операционные оценки, не тарифные цены. Измерять отдельно Neon compute/IO/storage/connections, Railway CPU/RAM/network и AI input/output tokens. Источники сами по себе не требуют MTProto connection: нужен план способа доступа и разрешения.

Соединения: MTProto — до `min(A,100)` долгоживущих handles в нынешней политике, до 5 одновременных startup попыток; SSE — `U` HTTP streams, но не `U` постоянных PostgreSQL connections; push — до 8 одновременных сетевых доставок. Все DB операции пользуются общим Prisma pool, поэтому верхняя граница одновременных DB connections равна его настроенному размеру на инстанс × число API инстансов, а не количеству источников/задач. Точное значение pool и CPU/RAM в MB или core-seconds неизвестно без deployment config и профиля; gate этапа 0 должен измерить idle/burst CPU, RSS/heap, socket memory и DB connections по каждому процессу. Целевой дополнительный CPU/RAM для idle AI, Discovery и Instagram webhook равен нулю сверх загруженного модуля; runtime socket и lease остаются постоянной стоимостью только при eligible аккаунтах.

| Процесс | Триггер, idle и остановка | PostgreSQL / connections | CPU/RAM/retention |
| --- | --- | --- | --- |
| Существующий MTProto runtime | Активный CRM аккаунт; socket и lease живут в idle; выключается при отключении всех аккаунтов/stop | 1 глобальный lease update/30 s ≈ 2 880/day, плюс startup/recovery; обычный Prisma pool не считать отдельным соединением на каждый socket | Постоянная socket/handle RAM приблизительно O(A); CPU idle измерить. Message table уже растёт, политику retention CRM сообщений согласовать отдельно. |
| Live event batch | MTProto update; idle: нет batch SQL; bounded 100/50 ms; stop с runtime | От `ceil(E/100)` до `E` транзакций в зависимости от группировки за 50 ms, плюс peer/read handling; точное число SQL зависит от состава событий | O(queue limit) памяти, bounded CPU; тексты сообщений сохраняются по действующей политике CRM. |
| Ежедневная CRM sync | Due scheduled task при eligible аккаунтах; idle до срока без work write; auto-disarm без eligible | По аккаунтам и страницам; максимум 2 000 scanned/1 000 imported на аккаунт за run. Start/end sync state writes выполняются и при неизменном refresh [initial-sync.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-initial-sync.service.ts#L143); неизменный checkpoint отдельно пропускает запись [batch-store.service.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-batch-store.service.ts#L407). | Сетевой/CPU всплеск, bounded concurrency; sync state сохраняется, task run retention по Operations. |
| SSE visible client | Открытый видимый CRM; hidden закрывает, reconnect narrow read | 0 DB heartbeat по текущему локальному hub; reconciliation запросы O(U) на reconnect | 1 HTTP stream/client и память O(U); не хранить бесконечный event log без необходимости. |
| Notification + push | Только новый значимый unread и opt-in; idle 0 новых writes; pending due/expiry использует существующий scheduler | Group upsert, recipient/subscription reads и claim только при событии; соединения из общего pool | Bounded fanout 8, notification TTL из существующей политики; подавлять дубликаты. |
| AI draft | Явное действие/ограниченный событием запуск; idle 0 requests/DB work; off по flag/budget | 1 bounded context read + usage/draft write на запрос | CPU tokenization/context size ограничить, RAM O(max context); draft expiresAt, usage агрегаты по retention. |
| Discovery | Разрешённый source due или ручной импорт; idle без source due 0 scans; stop по flag/source disable | O(observed pages + M batch writes), без per-post DB lookup; несколько общих pool connections, concurrency cap | Network/AI/CPU O(M), хранить evidence до expiresAt, candidates с review retention. |
| Instagram webhook | Только webhook/явный send; idle 0 app polling; off через account/flag | Idempotent event insert + conversation/message upsert, общий pool | Bounded webhook batch/retry, raw payload короткая TTL, message retention как CRM. |

Сценарии: **1 workspace / 2 собственных канала** — 1–несколько MTProto аккаунтов по фактическому подключению, без discovery sources и AI запросов idle cost в основном lease/socket плюс существующая daily sync. **1 workspace / 100 источников** — registry 100 строк, но активные проверки только по due/разрешённым событиям; O(100) scheduled coverage checkpoints за окно наблюдения, не 100 соединений и не 100 постоянных таймеров. **10 workspaces / 1 000 источников** — pagination и глобальный concurrency budget, source-weighted fair scheduling, 10 workspace ACL, O(1 000) stored source states; один общий runtime lease сейчас ограничен 100 CRM аккаунтами на startup, поэтому это отдельная capacity gate [runtime.policy.ts](../../apps/api/src/domains/telegram/telegram-crm/telegram-crm-runtime.policy.ts#L8). Нагрузка пропорциональна доступным новым материалам/запросам, а не одному лишь S. Для каждого сценария измерить p95 burst, storage growth/day и idle 24 h; без доли активных источников, объёма материалов, аккаунтов, тарифов Neon/Railway и model token mix денежный расчёт недостоверен.

## 8. Проверка и критерии приёмки

- API tests: live/snapshot/history, duplicate/edited/out-of-order MTProto updates, gap/recovery, lease loss, Telegram send succeeds + DB fails, workspace/own permissions, read watermark races, inbox cursor with equal timestamps and state transitions. Использовать существующие `telegram-crm-*.spec.ts` и MTProto adapter/normalizer specs.
- Frontend tests: one mounted SSE subscription per visible CRM, hidden close, reconnect reconciliation, narrow cache key updates, rapid conversation switch, cursor pages, mutation rollback, loading/error/empty, PWA push click/permission/duplicate. Проверять на 320, 360, 390, 768, 1024, 1440 px и keyboard.
- AI tests: permission/DNC, consent/source boundary, stale pricing, package composition, malicious quoted text, budget cap, failed provider call, redaction and no send without approval.
- Discovery tests: 30-day complete coverage vs missing day, duplicate advertiser across sources, mutual ad/unknown, suspicious contact, partial import/retry, bounded batch, retention/export isolation.
- Instagram tests: signature invalid/replay, subscription verification, own account mapping, webhook ordering, expired send eligibility, API failure/retry; fixtures from official supported API version.
- Baseline: measured p50/p95 first inbox open, switch, message render, SQL count/time/rows per endpoint, browser requests/refetch, 24 h idle Neon wakeups, DB connection max, Railway CPU/RAM/network, table bytes/day, push duplicates, AI tokens/draft. Acceptance targets to approve after baseline: no polling/refetchInterval; no per-row HTTP; one active visible stream; no lost message/read under retry; idle AI/discovery zero calls; p95 and DB work demonstrably lower than baseline for 25/100/1 000 conversations; no status/price leakage across workspaces; bounded storage and cost caps.
- Gates: `pnpm db:generate` after schema, API tests/typecheck/build, web lint/typecheck/component tests, `pnpm architecture:check` plus strict trajectory. This audit itself changes no production code and runs no migrations.

## 9. Риски, зависимости, открытые вопросы

Неизвестны: Railway replicas/routing и pool size, реальные Neon compute/IO/connection метрики, количество MTProto аккаунтов/диалогов и сообщений, 24 h idle baseline, ключевые `EXPLAIN` планы, consent/право на анализ сообщений и источников, policy retention CRM и AI, Meta App type/permissions/review, тарифы AI и допустимый месячный бюджет. До ответов нельзя утверждать конкретную причину всех задержек, точную экономию или цену сценариев. Особый риск — нельзя запускать ещё один MTProto runtime на тот же StringSession; lease сейчас решает эксклюзивность, но каждые 30 секунд будит БД. Снижение этой стоимости требует отдельного доказанного варианта эксклюзивности и failover, а не удаления lease.

Рекомендуемый порядок: baseline → подключить realtime и проверить multi-instance/reads → compact cursor inbox → выборочное восстановление push → статусы и package context → AI drafts → Discovery → Instagram после API approval. Каждый этап включать feature flag для одного workspace, сравнивать метрики и иметь rollback без потери данных.
