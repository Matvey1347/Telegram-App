# Internationalization architecture

## Scope and ownership

Telegram System localizes presentation without turning display text into a
business contract. Domain state, permissions, actions, statuses and failures
cross application boundaries as stable machine values. A presentation surface
maps those values to translation keys and renders the selected locale.

The internal web application and backend-owned outbound messages share locale
and key conventions, but not one runtime catalog. Consumer applications keep
their own localization resources inside their product boundary.

## Locale resolution

- `User.locale` is the canonical authenticated preference.
- The internal web locale cookie mirrors that preference so the Next.js server
  layout can select a locale before the first client render.
- Changing language updates the client provider and cookie immediately, then
  persists the preference through the account API.
- Authentication responses carry the locale so login and registration can set
  the cookie before navigation.
- Unsupported or missing locales fall back to English through the shared locale
  normalizer.

The cookie is presentation state, not authentication. HTTP API responses do
not vary by the locale cookie or `Accept-Language`.

## Namespaces and loading

Catalogs are feature-owned and split by namespace. `common` is limited to
genuinely global actions and states. Navigation copy belongs to `navigation`;
public login, registration and password recovery belong to `auth`; Telegram
Posts uses focused common, editor, groups, calendar and optional subfeature
namespaces. Profile settings and their structured account errors belong to the
route-scoped `account` namespace.

The internal shell eagerly needs only its small common/navigation resources.
Route and feature registries declare additional namespaces. The web loader uses
separate dynamic imports per locale and namespace, so unrelated feature packs
do not enter a page chunk. Route layouts resolve their declared catalogs on the
server and pass them through a preloaded boundary, so translated feature UI and
its data queries can render immediately without a hydration/catalog waterfall.
Heavy modal or import resources can still be requested only when that surface
opens. The alternate locale is loaded on an explicit switch rather than
competing with the active route during first load.

Public auth routes preload the `auth` namespace from the locale cookie before
rendering. Their flag switcher updates only presentation cookie state because
no authenticated preference endpoint is available yet. Registration sends the
selected locale as part of account creation; login replaces the cookie with the
existing account preference returned by the backend.

The account route similarly preloads only its `account` catalog and generates
localized page metadata on the server, while common/navigation continue to be
owned by the shell.

English catalogs define the canonical key and interpolation shape. Every other
locale must have exact key and placeholder parity. Keys are semantic and remain
stable when wording changes.

## Machine values and errors

The backend never branches on translated or human-readable text. Examples:

```text
PAID                         -> adSales.status.paid
TELEGRAM_MANAGED_POST_FAILED -> telegramPosts.status.failed
TELEGRAM_POST_TITLE_REQUIRED -> telegramPosts.errors.titleRequired
```

HTTP failures expose a stable `code` and structured interpolation parameters.
An English `message` may remain temporarily for compatibility and diagnostics,
but localized clients resolve `code` first. Unknown failures use a localized
safe fallback and retain the correlation id for support; raw English backend or
upstream text is not presented as Russian UI.

Persisted diagnostic text such as an upstream error is not business state.
Logic uses explicit status/code fields, and user-facing rendering uses the code
plus parameters.

## Backend-owned output

Only output rendered without a frontend is translated on the backend: Telegram
bot messages, email, push/PWA notifications and server-generated exports.
Backend catalogs stay with their owning feature, are split into namespaces and
use the same canonical locale preference. Recipient locale is selected as part
of the existing useful-work query; localization must not introduce per-user
queries, polling or recurring jobs.

Machine-oriented files and prompts intended for another parser or language
model are protocol payloads rather than user-facing exports. Their invariant
English field instructions are versioned with that protocol; any title,
description or report text shown directly to a person belongs to a localized
export namespace and must resolve the recipient locale.

## Validation

`pnpm i18n:check` validates registered namespaces, locale parity, empty or extra
keys, interpolation placeholder parity, stable machine-value mappings and
invalid namespace references. Unused-key detection is best effort because
registry-driven and machine-value mappings are intentionally dynamic; suspected
unused keys are warnings until the scanner can prove a safe deletion.

Feature tests cover English and Russian rendering, instant switching and cookie
synchronization, representative machine-error mapping, date/plural formatting,
and lazy namespace loading. Backend tests cover locale persistence, unsupported
locale rejection, structured failure codes and locale-specific outbound copy.

## Runtime cost

Localization adds no timer, cron, polling, background worker or unchanged-state
write. Static catalogs are loaded only by the feature that uses them. Locale is
included in existing auth/account or notification reads, so the 100-channel
case adds no database queries, external calls or recurring Railway/Neon work.
The only new database write is an explicit user language change.
