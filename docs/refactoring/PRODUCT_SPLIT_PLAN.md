# Product split plan

## Current dependency map

This plan is an implementation order, not authorization to delete production data. Historical Prisma migrations remain immutable. Any forward data migration requires a backup, dry-run, rollout, rollback, and explicit approval before destructive steps.

| Boundary | Verified ownership and links | Split constraint |
| --- | --- | --- |
| Internal Finance | `apps/api/src/domains/finance/*`; internal web Finance surfaces | It is Nexeloq's internal finance system. It is not consumer Finance and must retain its API, data, and implementation. |
| Retired Simple Finance | Runtime/UI/package/aliases and `/simple-finance/[botId]` entrypoints are removed; the legacy application type is no longer offered. | `SimpleFinance*`, its enum values, and historical migration remain as a non-runtime data layer pending a separately approved retention or deletion plan. |
| Consumer Finance | `products/finance/{api,bot,web}`; `@telegram-system/finance`; `@consumer-finance/*`; `FINANCE`; `/finance/[botId]` entrypoint | This is the sole consumer implementation. Its public URL, FinanceProfile/transaction records, IDs, and subscription contracts are unchanged. |
| Retired Greeter | Source product, routes, UI, registry/dispatcher branches, scheduler branches, and shared contracts were removed in Step 1. The database still has `GREETER` and its historical rows. | The forward transition migration makes legacy data unreachable at runtime; no data tables, enum values, or historical migrations are removed without later approval. |
| Retired Greeter data boundary | Prisma retains `GreeterConfig*`, `GreeterChannel*`, `GreeterJoinRequest`, `GreeterSequence*`, `GreeterBroadcast*`, `GreeterTestSession`, and `GreeterUserEnvironmentState`, related to Workspace, TelegramChannel, TelegramBotIntegration, TelegramBotUser, and TelegramBotDelivery. | The former scheduler and delivery-core product branches are removed. The generic scheduler/delivery core remains free of Greeter product imports. |
| Telegram composition | `apps/api/src/domains/telegram/telegram-bots/telegram-bots.module.ts` wires product providers; core registry/dispatcher uses application types | Only the composition root may bind product adapters. Core must stay product-implementation-free. |
| Shared/database | `packages/shared/src/types/{consumer-finance,telegram-bot-platform}.ts`; `apps/api/prisma/schema.prisma` | Shared contracts are serializable only. Prisma models are API-internal and Greeter data removal is deferred pending an approved migration. |

Exact `RID` search (`\bRID\b`, case-insensitive) found no separate entity, tag, feature, model, type, or import. No approximate match is to be removed.

## Implementation order

| Step | Scope, risk, and mitigation | Automated checks | Completion criterion |
| --- | --- | --- | --- |
| 1. Greeter removal — source complete; rollout pending | Risk: break Telegram dispatch, scheduled delivery, workspace UI, or live Greeter records. Product runtime/UI/contracts and named scheduler/delivery branches are removed; the non-destructive forward DB transition must be applied only through the documented backup/dry-run rollout. | Targeted core tests; API test/build/typecheck; web test/typecheck/build; shared build; `pnpm architecture:check`; import search. | Source has no Greeter UI, routes, providers, controllers, registry/dispatcher path, package/import, or runtime usage. Applying the documented forward migration makes legacy DB objects unreachable at runtime. |
| 2. Simple Finance removal — source complete; rollout pending | Risk: delete the wrong consumer product or lose account/transaction/premium data. Runtime/UI/package/aliases, `SIMPLE_FINANCE`, and simple-finance routes are absent; internal Finance and consumer Finance remain independent. The forward transition preserves all Simple Finance data. | Targeted core/migration tests; Prisma validate/generate; API/web/shared build/typechecks; route check; architecture check; import search. | Applying the documented non-destructive transition makes old integrations unreachable while all legacy tables and records remain available for a later approved retention decision. |
| 3. Finance rename — source complete | Risk: break package aliases, Nest imports, URL compatibility, Telegram type semantics, or existing consumer data. The retained product is now `products/finance`, package `@telegram-system/finance`, and neutral `@consumer-finance/*` aliases; `/finance/[botId]` and `FINANCE` are preserved. | Consumer Finance tests; API/web/shared build/typechecks; route tests; architecture check; import search for old aliases. | One consumer Finance implementation has a clear name; internal Finance is unchanged; prior consumer accounts, transactions, and entitlements remain addressable. |
| 4. Independent Finance API/Web/DB/Telegram | Risk: accidental product/platform coupling, cross-product imports, or recurring runtime cost. Make contracts explicit; keep bot adapter thin and composition-only wiring in the module root. | Product API/web/bot tests; Prisma validation/generation for approved schema work; integration tests; architecture check; runtime-cost review. | Consumer Finance has independently owned API, web, database contract, and Telegram adapter with no forbidden internal/product imports or new idle work. |
| 5. Support Center | Risk: prematurely turning one product's policy into a shared platform. Start only from approved use cases and stable ports; preserve tenant/workspace isolation. | New focused tests, host builds/typechecks, architecture check, contract and runtime-cost review. | Shared Support Center behavior is proven by real consumers, contract-tested, isolated, and does not import product implementation. |
| 6. Partner Platform | Risk: cross-product data/access leakage and a generic framework without proven semantics. Introduce only stable multi-product contracts and composition ports. | Contract/isolation tests, host builds/typechecks, architecture check, integration and runtime-cost review. | Partner Platform supports approved product integrations through stable ports without product-to-product implementation imports or new unbounded runtime work. |

## Greeter retirement database transition

The non-destructive forward migration `20261017000000_retire_greeter_runtime` preserves every Greeter table, enum, relation, scheduled-task history, and historical migration. Before applying it, quiesce/scale down delivery schedulers and Telegram webhook/runtime instances, then wait for in-flight delivery and webhook work to finish; a migration cannot unsend a message that an old worker already gave to Telegram. Take a database backup and record a dry-run count for Greeter integrations, pending/retry/processing deliveries linked by integration or Greeter relations, and the three Greeter `ScheduledTaskConfig` rows. Apply it to a restored staging backup first, verify the resulting counts, then deploy the runtime that contains no Greeter handlers.

The migration cancels only queued/claimed/retryable Greeter-linked deliveries, changes `GREETER` bot integrations to `NONE`, and disarms the retired task configs. `TelegramBotApplicationWorkspaceAccess` Greeter rows remain retained audit data; the registry no longer exposes that application type. It does not drop data. Rollback is a restore from the verified pre-migration backup followed by redeploying the prior runtime; do not re-enable a retired integration in the new runtime. Table/enum/model removal requires separate production data analysis and explicit approval.

## Simple Finance retirement database transition

The non-destructive forward migration `20261017010000_retire_simple_finance_runtime` retains every `SimpleFinance*` table, enum, relation, record, and historical migration. Before applying it, quiesce old Simple Finance webhook/runtime workers and wait for in-flight updates to finish. Take a verified database backup; record dry-run counts for `SIMPLE_FINANCE` integrations and all four legacy tables; then apply the migration to a restored staging backup before production.

It changes only `TelegramBotIntegration.applicationType` from `SIMPLE_FINANCE` to `NONE`. `TelegramBotApplicationWorkspaceAccess` legacy rows remain audit data and the registry does not expose the type. The migration has no `DROP` or `DELETE`; it does not modify the retained consumer Finance `FINANCE` integrations, `FinanceProfile`, transactions, public `/finance/[botId]` URL, IDs, or subscriptions. Rollback is restore from the verified pre-migration backup followed by redeploying the prior runtime. Any later table/type/model removal requires production-data analysis and explicit approval.
